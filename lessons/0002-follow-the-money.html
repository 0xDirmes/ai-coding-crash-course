Follow the money

One purchase, traced from URL to SQLite row. After this you can find where any page in Cadence gets its data.

Cadence is a small Udemy: instructors publish courses, students buy and take them, and teams buy seats as coupons. Every feature you build will follow the same five-layer path, so learn it once on the code path you care about most: money.

1. URL → file

Routes are configured in one file, not inferred from folder names. Each entry maps a URL pattern to a route module:

route("courses/:slug/purchase", "routes/courses.$slug.purchase.tsx"),
app/routes.ts:15

Most routes sit inside layout("routes/layout.app.tsx", [...]), which wraps them in the sidebar shell. When you add a page, you add a line here.

2. The route module: three exports, two run on the server

ExportRunsIn the purchase route
loaderServer, on GETLooks up the course, resolves the buyer's country, computes the PPP price for display (line 57)
actionServer, on POSTValidates the form with Zod, recomputes the price, writes the purchase (line 120)
defaultServer render + browserRenders loaderData; submits via useFetcher (line 161)

Types come from generated files: import type { Route } from "./+types/courses.$slug.purchase" gives you Route.LoaderArgs and Route.ComponentProps, with loaderData inferred from what the loader returns. Run npm run typecheck (which runs react-router typegen) if they look stale.

The fintech instinct, confirmed. The form posts only an intent (and quantity for teams), never a price. The action calls calculatePppPrice(course.price, country) again on the server (line 142). The price the user sees and the price charged come from the same function, but only the server's copy is trusted.

The action's input is a Zod discriminated union on intent, parsed via the project helper parseFormData (app/lib/validation.ts):

const purchaseActionSchema = z.discriminatedUnion("intent", [
  z.object({ intent: z.literal("confirm-purchase") }),
  z.object({ intent: z.literal("confirm-team-purchase"),
             quantity: z.coerce.number().int().min(1) }),
]);
app/routes/courses.$slug.purchase.tsx:41

Redirects and HTTP errors are thrown: throw redirect(...), throw data("Course not found.", { status: 404 }). That's the house style for control flow in loaders and actions.

3. Services: plain functions, positional params

createPurchase(currentUserId, course.id, pppPrice, country);
enrollUser(currentUserId, course.id, false, false);
throw redirect(`/courses/${slug}/welcome`);
app/routes/courses.$slug.purchase.tsx:149–151

Route modules hold HTTP concerns; app/services/*Service.ts hold the business logic and the queries. Services take positional arguments (a documented convention in purchaseService.ts) and import a shared db.

4. Drizzle + SQLite: synchronous, integer cents

return db.insert(purchases)
  .values({ userId, courseId, pricePaid, country })
  .returning()
  .get();
app/services/purchaseService.ts · createPurchase

The driver is better-sqlite3, which is synchronous, so queries end in .get() / .all() / .run() with no await. Money is integer cents throughout (courses.price, purchases.pricePaid, schema.ts:65); formatPrice divides by 100 only at display time.

Something to notice. createPurchase and enrollUser are two separate writes with no transaction. enrollUser can throw (for example, "User is already enrolled"). Keep that in mind for the quiz.

5. How the tests reach the database

Service tests never touch data.db. They swap the ~/db module for a fresh in-memory SQLite built from the real migrations:

vi.mock("~/db", () => ({ get db() { return testDb; } }));
beforeEach(() => { testDb = createTestDb(); base = seedBaseData(testDb); });
app/services/purchaseService.test.ts:9 · app/test/setup.ts

This is the pattern you'll copy for every feature: write the service, then test it against createTestDb().
